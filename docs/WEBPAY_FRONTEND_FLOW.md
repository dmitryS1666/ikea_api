# WebPay: инструкция для фронтенда

Этот документ описывает клиентский сценарий оплаты заказа через WebPay в текущей реализации API.

## Что важно понять заранее

- Фронт не отправляет поля `wsb_*` напрямую в WebPay.
- Фронт получает от API поле `order.payment_url` и открывает его.
- `payment_url` ведет на backend-страницу `GET /api/v1/payment_links/:id?token=...`, которая сама делает auto-submit формы в WebPay.

## Полный сценарий (happy path)

1. Пользователь оформляет заказ через `POST /api/v1/checkout`.
2. В ответе приходит объект `order` с полями:
   - `id`
   - `status` (`created`)
   - `payment_url`
   - `payment_expires_at`
3. Фронт открывает `payment_url` в браузере / webview.
4. Пользователь оплачивает на стороне WebPay.
5. Дальше есть 2 пути подтверждения:
   - основной: backend получает серверный notify (`POST /api/v1/webhooks/webpay`) и сам переводит заказ в `paid`;
   - fallback: если notify недоступен (например, local backend), фронт на `return_url` получает `wsb_tid` и вызывает `POST /api/v1/account/orders/:id/confirm_webpay`.
6. Фронт обновляет заказ через `GET /api/v1/account/orders/:id` и показывает финальный статус.

## Что сделать на фронте

### 1) После checkout всегда проверять наличие `payment_url`

Если `payment_url` отсутствует, показывать ошибку оформления заказа и не открывать оплату.

### 2) Проверять срок годности ссылки

Использовать `payment_expires_at`:
- если истекла, не открывать старую ссылку;
- предложить пользователю оформить заказ заново.

### 3) Открывать `payment_url` как URL страницы

Не парсить HTML и не пытаться отправлять WebPay-форму вручную. Страница `payment_links/show` делает это автоматически.

### 4) После возврата пользователя обновлять статус заказа

Минимум:
- вызвать `GET /api/v1/account/orders/:id`;
- если статус уже `paid`, показать успех.

Если статус не `paid`, а на странице возврата есть `wsb_tid`:
- вызвать `POST /api/v1/account/orders/:id/confirm_webpay` с JWT и body:

```json
{
  "transaction_id": "858578101"
}
```

Потом снова запросить `GET /api/v1/account/orders/:id`.

## Контракты API для фронта

### Checkout

- `POST /api/v1/checkout`
- Успех: `201`, в `order` есть `payment_url`.

### Просмотр заказа

- `GET /api/v1/account/orders/:id`
- Используется для финального статуса (`status`) и метаданных оплаты:
  - `webpay_transaction_id`
  - `webpay_paid_at`

### Ручное подтверждение оплаты (fallback)

- `POST /api/v1/account/orders/:id/confirm_webpay`
- Требует JWT пользователя.
- Body: `{ "transaction_id": "<wsb_tid>" }`.

Ожидаемые ответы:
- `200`: оплата подтверждена / заказ уже оплачен;
- `422`: платеж не подтвержден или не совпала сумма/валюта;
- `409`: транзакция уже привязана к другому заказу;
- `502`: backend не смог получить статус транзакции в WebPay;
- `503`: не настроены `WEBPAY_BILLING_USERNAME` и `WEBPAY_BILLING_PASSWORD`.

## Рекомендуемая UI-логика статусов

- `created` + ссылка валидна -> "Ожидает оплату".
- `created` + ссылка истекла -> "Ссылка на оплату истекла".
- `paid` -> "Оплачено".
- Любой иной статус -> отображать как статус обработки заказа.

## Обработка ошибок на фронте

- Если `GET /api/v1/payment_links/:id?token=...` вернул:
  - `404` -> ссылка не найдена;
  - `403` -> токен недействителен;
  - `410` -> ссылка устарела.
- Для `confirm_webpay` показывать текст ошибки из API, но сохранять кнопку "Обновить статус".

## Тестовый чек-лист для фронтенд-разработчика

1. Оформить заказ и убедиться, что пришел `payment_url`.
2. Открыть `payment_url` и пройти тестовую оплату в sandbox WebPay.
3. Вернуться в приложение и проверить, что заказ перешел в `paid` после обновления.
4. Проверить fallback:
   - взять `wsb_tid` с `return_url`;
   - вызвать `confirm_webpay`;
   - убедиться, что статус стал `paid`.
5. Проверить сценарий просроченной ссылки (`410`) и корректный UX.
