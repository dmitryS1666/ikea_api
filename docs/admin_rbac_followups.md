# Ролевая модель: доп. проработка

Ниже зафиксированы зоны риска и задачи следующего этапа после внедрения базовой RBAC-модели.

## 1) Персональные данные в исторических сущностях

- Сейчас право `view_personal_data` контролирует доступ к полям в `users_admin`, но часть ПД остается в связанных разделах (`orders`, `return_requests`, `cooperation_requests`).
- Для полного соответствия модели нужно маскирование ПД в каждой таблице/форме этих разделов.

## 2) Ограничения на уровне API

- Внедрение сделано для Trestle (админка), но не покрывает API-эндпоинты вне Trestle.
- Нужно вынести политику в общий слой (policy/service) и переиспользовать в контроллерах API.

## 3) Аудит изменений прав

- Добавлены кастомные ограничения (`users.custom_permissions`), но сейчас нет аудита "кто и когда изменил права".
- Рекомендуется добавить таблицу `permission_change_logs` или versioning (PaperTrail) для юридической трассируемости.

## 4) Финансовая роль (бухгалтер)

- Роль `accountant` имеет доступ к финансовому просмотру, но специализированный отчет "реестр" в админке еще не реализован.
- Следующий шаг: выделить отдельный отчетный экран/выгрузку с минимальным набором ПД.

## 5) Гранулярность прав для разделов

- Текущая матрица разрешений сгруппирована укрупненно (контент/заявки/техника/финансы).
- При росте команды потребуется более тонкая детализация (например, отдельно управление промокодами, SEO, каталогом).
