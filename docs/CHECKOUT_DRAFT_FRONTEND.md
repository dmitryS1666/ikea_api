# Оформление заказа: черновик и оплата WebPay

Документ описывает доработки API для пошагового чекаута и работу с оплатой. Обратная совместимость со старым сценарием сохранена.

## Совместимость

| Раньше | Сейчас |
|--------|--------|
| `POST /api/v1/checkout` без флага `draft` | Без изменений: один запрос создаёт заказ, выдаёт `payment_url`, очищает корзину |
| — | Опционально многошаговый сценарий с полем `draft: true` и отдельным завершением |

Новое поле в ответах заказа: **`checkout_draft`** (boolean). Пока `true`, заказ не финализирован: ссылка на оплату и таймер оплаты не выданы (`payment_url` обычно `null`).

## Ограничение: один черновик на пользователя

Одновременно может существовать не более **одного** активного черновика (`checkout_draft: true`). Повторный `POST /checkout` с `draft: true` при уже существующем черновике возвращает **200** и тот же заказ (идемпотентность), а не создаёт новый.

Пока черновик активен, **старый** `POST /checkout` **без** `draft` вернёт **409 Conflict** с телом:

```json
{
  "error": "Сначала завершите или отмените оформление заказа в корзине",
  "code": "checkout_draft_exists",
  "draft_order_id": 123
}
```

Сначала завершите черновик (`finalize`) или отмените его (`DELETE`), либо вернитесь к одношаговому чекауту только после отмены черновика.

## Эндпоинты

### 1. Создать черновик из корзины

`POST /api/v1/checkout`

Тело — как раньше, плюс **`draft: true`** (или строка `"true"`).

Обязательные поля такие же, как для полного чекаута по типам доставки, **если** вы передаёте `delivery_type` сразу (необязательно на первом шаге).

Минимальный первый шаг:

```json
{ "draft": true }
```

Оформление **только выбранных** позиций корзины (чекбоксы на фронте):

```json
{
  "draft": true,
  "items": [
    { "sku": "90205097", "quantity": 1 },
    { "sku": "09588114", "quantity": 2 }
  ]
}
```

Без `items` в заказ попадает **вся** корзина (как раньше). С `items` в заказ переносятся только указанные SKU/количества; остаток остаётся в корзине. Суммы, доставка, пошлина и доступные способы доставки считаются **только по переданным `items`**.

Для пересчёта summary на экране корзины (до черновика): `POST /api/v1/cart/summary` с тем же массивом `items` и `cart_token`.

После успеха:

- В заказ перенесены выбранные позиции (или вся корзина, если `items` не передан).
- Невыбранные позиции остаются в корзине.
- Ответ **201 Created** (или **200 OK**, если черновик уже был — см. выше).
- В теле — `order_id`, `order`, поле `checkout_draft: true`.

Опционально в том же запросе можно передать `delivery_type`, адрес / ПВЗ и т.д. — тогда после создания выполнится пересчёт как при обновлении черновика.

### 2. Текущий черновик

`GET /api/v1/checkout/draft`

- **200** — JSON в формате FastJsonapi (как сериализатор заказа с `order_items`).
- **404** — активного черновика нет.

### 3. Обновить черновик (доставка, контакты, оплата)

`PATCH /api/v1/checkout/:id`

`:id` — `order_id` черновика. Тело — те же поля, что и у `POST /checkout` (кроме `draft`): `delivery_type`, `payment_method`, `full_name`, `phone`, `pickup_point_id`, `delivery_address_id`, `address`, `pickup_point`, `passport`, коды верификации и т.д.

Правила:

- Если передан **`delivery_type`**, выполняются проверки доступности способа доставки и контекста (ПВЗ / адрес), пересчитываются суммы.
- Если **`delivery_type` не передан**, обновляются только переданные контакты и фрагменты `address` (черновик остаётся с прежним типом доставки или без него).

### 4. Завершить оформление (выдать оплату)

`POST /api/v1/checkout/:id/finalize`

Тело — полный набор данных, как при классическом `POST /checkout` (ФИО, телефон, доставка, оплата, паспорт при необходимости). Недостающие значения подставляются из уже сохранённого черновика.

Если черновик создан по `items`, при `finalize` передайте **тот же** массив `items` (SKU и количества должны совпадать с черновиком), иначе **422** с `code: items_mismatch`.

После успеха:

- `checkout_draft` становится `false`.
- Вызывается выдача ссылки WebPay (`payment_url`, `payment_expires_at`, `payment_order_number` и т.д.).
- Отправляется уведомление о заказе (как при старом чекауте).

Ответ **201 Created**, формат как у успешного `POST /checkout` без черновика.

### 5. Отменить черновик и вернуть товары в корзину

`DELETE /api/v1/checkout/:id`

- Позиции заказа возвращаются в корзину (как при «повторить заказ»), промокод заказа возвращается на корзину при наличии.
- Заказ переводится в статус **отменён**, `checkout_draft` снимается.

Ответ **204 No Content**.

## Переход на оплату WebPay (фронт)

После **`finalize`** или классического **`POST /checkout`** в объекте заказа приходит **`payment_url`**.

Рекомендуемый UX:

1. Открыть **`payment_url`** в браузере пользователя (новое окно / редирект / WebView), например:
   - `{WEBPAY_LINK_BASE_URL}/api/v1/payment_links/{order_id}?token={payment_link_token}`
   - точное значение уже собрано в `payment_url` на бэкенде (`WebpayPaymentLinkService`).
2. Эта страница отдаётся API (**HTML**): внутри — автосабмит формы **POST** на шлюз WebPay (`WEBPAY_PAYMENT_PAGE_URL`), поля подписаны на сервере. Пользователь попадает на страницу ввода карты WebPay.

Не нужно собирать форму оплаты на фронте вручную — достаточно перейти по `payment_url`.

### Как бэкенд узнаёт об оплате

Каналы независимы от того, отправляет ли браузер POST на WebPay (это стандартная оплата через их страницу):

1. **Серверный callback WebPay (основной источник истины)**  
   В форму оплаты подставляется **`wsb_notify_url`** — по умолчанию  
   `{WEBPAY_LINK_BASE_URL}/api/v1/webhooks/webpay`  
   (или переопределение через конфиг `notify_url`, см. `config/initializers/webpay.rb`).  
   WebPay вызывает этот URL **с сервера**, подпись проверяется в `WebpayPaymentCompletionService`. При успехе заказ переводится в статус **оплачен**, заполняются `webpay_transaction_id`, `webpay_paid_at`.

2. **Возврат пользователя в приложение**  
   После оплаты пользователь может вернуться по **`wsb_return_url`** / **`wsb_cancel_return_url`** (настраиваются окружением). На статус оплаты это не опирайтесь как на единственный источник — только как на UX.

3. **Подтверждение с клиента (резерв)**  
   Если notify недоступен: **`POST /api/v1/account/orders/:id/confirm_webpay`** с `{ "transaction_id": "..." }` — см. комментарии в `OrdersController` и переменные Billing API в конфиге WebPay.

### Что показывать пользователю после оплаты

Опирайтесь на **`GET /api/v1/account/orders/:id`** (поля `status`, `webpay_transaction_id`, `webpay_paid_at`). Для черновика до `finalize` оплата недоступна; после успешного notify заказ станет оплаченным независимо от того, как фронт открыл `payment_url`.

### Номер заказа в ЛК (`public_uid`)

В ответах сериализатора заказа **числовой внутренний `id` не отдаётся** в атрибутах. Для пользователя используйте:

- **`public_uid`** — строка из **6–8 цифр**, уникальна в системе (отдельное поле в БД, не заменяет `orders.id`).
- В JSON:API у ресурса заказа поле **`data.id`** также равно **`public_uid`** (не числовому id).

Запросы **`GET/PATCH …/account/orders/:id`**, **`confirm_webpay`**, **`reorder`**, а также **`order_id`** при создании возврата принимают в `:id` / `order_id` либо **`public_uid`**, либо по-прежнему **числовой id** (для обратной совместимости). Если строка из 6–8 цифр совпадает и с `public_uid`, и с чужим числовым id, сначала ищется совпадение по **`public_uid`**.

Внутренние сценарии (черновик checkout **`PATCH /checkout/:id`**, ссылки оплаты **`/payment_links/:id`**) по-прежнему используют **числовой** `order.id`.

## Поля заказа для UI

| Поле | Смысл |
|------|--------|
| `public_uid` | Публичный номер заказа (6–8 цифр), показывать пользователю вместо внутреннего id |
| `checkout_draft` | `true` — многошаговый процесс не завершён |
| `payment_url` | Ссылка для перехода к оплате (после `finalize` или классического checkout) |
| `payment_expires_at` | Для черновика не задаётся; после выдачи ссылки — срок действия оплаты |
| `webpay_paid_at` / `webpay_transaction_id` | Факт оплаты после колбэка WebPay |

