# Poland-треки ShopByShop после оплаты

Endpoint: `POST https://profile.shopbyshop.by/api/external/poland/ikea-tracks`.

## Отправка без email (изменение 04)

По согласованному требованию отсутствие email в профиле больше не блокирует
локальную отправку: ключ `recipient.email` исключается из нового снимка, если
значение пустое. Подставные адреса не используются. Заполненный некорректный email
по-прежнему блокирует запрос. В предоставленной спецификации ShopByShop email
обязательный; при отказе API с HTTP 422 экспорт станет `blocked` без автоматических
повторов. Локальный `ready` означает готовность к попытке, а не принятие внешним API.
Успех подтверждается только валидным HTTP 201 и состоянием `succeeded`.

Изменение применяется к новым снимкам. Уже сохранённые снимки автоматически не
переписываются. Для существующего `blocked` после выкладки выполнить
`poland_tracks:retry[ORDER_ID]`, чтобы пересобрать снимок. `uncertain` требует сверки
с ShopByShop, его нельзя повторять таким способом. Ранее сохранённый валидный email
остаётся частью снимка даже при последующем удалении email из профиля.

## Что реализовано

При переходе заказа в `paid` создаётся одна запись `PolandTrackExport` в той же
транзакции БД. Снимок получателя и товаров зашифрован через Active Record Encryption.
После commit ставится фоновая задача. Для типов 1 и 4, если Европочта ещё не вернула трек, задача
ждёт; запись трека в заказ запускает отправку. Проверка ожидающих заданий каждую
минуту через существующий CronSchedule восстанавливает постановку в очередь после
недоступности Redis. Сам Poland API не вызывается из HTTP-обработчика оплаты.

Существующая проверка подписи Webpay, суммы, валюты и допустимого статуса не менялась.
Ручной перевод заказа в `paid` через штатное сохранение модели также создаёт задание.
Уже оплаченные до установки заказы автоматически не выгружаются.

Поддержаны все три варианта актуального контракта:

| Доставка в проекте | delivery_type API | Поля доставки |
| --- | --- | --- |
| europost_pickup | 1 | weight + europost_track + pvz; delivery_address отсутствует |
| courier | 4 | weight + europost_track + delivery_address; ключ pvz отсутствует |
| ikeya_delivery | 5 | weight + delivery_address; ключи pvz и europost_track отсутствуют |

Корневое поле `weight` — общий вес заказа в граммах, строка (например `"1000"`),
сразу после `delivery_type`. Источник: `order.weight` (кг) → граммы; иначе
`address_json.weight_kg` / `pricing_snapshot.total_weight_kg`. Без положительного
веса экспорт блокируется. Старые снимки без `weight` дополняются из заказа перед POST.

Тип 5 отправляется после оплаты без ожидания Европочты; Webpay больше не ставит
EuropostCreateShipmentJob для собственной доставки IKEYA. Адрес доставки сохраняется
при оплате из `address_json.delivery.address` (либо legacy-полей самого address_json),
не берётся из прописки. Поддерживаются house/house_number/address_house_number,
apartment/flat/flat_number, корпус и готовые address_full/full_address.
Неполный адрес блокирует отправку. Если после оплаты изменился тип доставки,
экспорт блокируется до проверки и явного retry, чтобы не смешивать способы доставки.

| Поле API | Источник |
| --- | --- |
| weight | кг заказа × 1000, строка граммов; обязателен для всех типов 1/4/5 |
| nomerikea | `order.public_uid`, fallback `order.id.to_s`: ровно как название сделки в CrmIntegrationService |
| europost_track | `order.resolved_track_number` |
| pvz для отделения | Сохранённый `store_id_finish` успешного запроса Европочты; иначе `pickup_point_id` / snapshot external_id / id |
| pvz для обоих курьеров | Ключ отсутствует |
| delivery_address для обоих курьеров | Снимок фактического адреса доставки при оплате |
| recipient | Профиль пользователя и расшифрованный паспорт; снимок на момент оплаты |
| адрес прописки | `user.region/city/street/house/building/apartment/postcode`, а не адрес доставки |
| building / corpus | `user.house` / `user.building` соответственно |
| document_country | Поле паспорта либо определяется по серии: две буквы BY, четыре цифры RU |
| address_country | Поле паспорта либо страна профиля (`RB` → `by`, `РФ` → `ru`); при отсутствии — страна документа |
| phone_country | По коду телефона +375 / +7 |
| items[].price | `order_item.poland_price_pln`: цена IKEA в PLN, без BYN-наценки и доставки |
| items[].link | `order_item.poland_product_url`: снимок Product.url |
| items[].name/count | `catalog_title` (name_ru + small_desc_name, как в AmoCRM) / `quantity` |

Поддержаны существующие ключи паспорта `passport_number` или `number`, `series`,
`issued_date` или `issued_at`, `issued_by`, `id_number`; также прямые имена API.
Полный номер `MP1234567` разбивается на серию и номер. Полный номер РФ из десяти
цифр разбивается на четыре и шесть. Даты ISO переводятся в ДД.ММ.ГГГГ.
Проверяются обязательные поля, страны BY/RU, формат паспорта/телефона, даты,
количество и цена ≥ 1. Недостаточные данные блокируют экспорт, но не отменяют оплату.

Поля PLN и URL сохраняются при создании позиции. Оба пути checkout передают
рассчитанную `unit_price_pln` явно. После оплаты изменение каталога/профиля не
изменяет уже сохранённый запрос. Валюта `order_items.price` остаётся BYN.

## Установка

1. Развернуть изменённые файлы и новые классы/миграции. Выполнить миграции до
   возобновления приёма заказов новым кодом:

   ```bash
   RAILS_ENV=production bundle exec rails db:migrate
   ```

2. На сервере Rails и Sidekiq должны быть одинаковые настройки:

   ```dotenv
   POLAND_TRACKS_ENABLED=true
   POLAND_TRACKS_API_KEY=<предоставленный API-ключ>
   ```

   Git-патч не меняет `.env` и не содержит реального ключа. Задать обе переменные
   в действующем серверном окружении; пример находится в `.env.poland.example`. Существующие ключи Active Record Encryption должны
   оставаться стабильными: ими шифруются паспорт и снимок запроса.

3. Перезапустить Rails и Sidekiq. При старте Sidekiq штатный CronManagerService
   зарегистрирует расписание `poland_track_exports` каждую минуту. Если расписания
   синхронизируются отдельно, выполнить:

   ```bash
   RAILS_ENV=production bundle exec rails runner 'CronManagerService.sync_all_schedules'
   ```

4. Проверить новый оплаченный заказ с полными паспортными данными и пропиской.
   После получения трека Европочты в админке заказа → «Poland-трек» должны появиться
   статус «Создан», внутренний трек и номер ShopByShop. Ответ
   хранится в `poland_track_exports.remote_response`.

`POLAND_TRACKS_ENABLED=false` останавливает создание и обработку новых заданий;
уже выполняющийся HTTP-запрос от этого не отменяется. Для включения/выключения
перезапустить оба процесса. Оплаты, совершённые при выключенной интеграции,
не подхватываются задним числом автоматически.

## Повторные запуски и ошибки

Уникальный индекс по `order_id` исключает второе локальное задание. Перед POST
под блокировкой строки сохраняется `sending`, затем транзакция завершается.
Другой worker увидит это состояние и не отправит запрос. Успешный `201` проверяется
на обязательные поля и совпадение номера заказа; для 1/4 также на совпадение трека.
Для типа 5 допускается отсутствующий или null cdek_number в ответе: формат ответа
для своей доставки пока не предоставлен, его нужно подтвердить при интеграционном прогоне. Сохраняются только оговорённые
поля ответа; сырые ответы и паспортные данные в диагностику не записываются.

| Состояние | Действие |
| --- | --- |
| pending | Ожидание фоновой обработки или номера Европочты |
| blocked | Исправить поля/настройки или причину HTTP 400/401/403/404/405/422; затем выполнить retry |
| sending | Запрос начат; повторный POST запрещён |
| succeeded | Трек создан, повторные задачи ничего не отправляют |
| uncertain | Таймаут, обрыв, HTTP 5xx/409/429/redirect, неверный 201 или прерванный worker; сначала сверить результат на ShopByShop |
| cancelled | Заказ отменён, возвращён в неоплаченный статус, снова стал черновиком или поменялся на неподдерживаемую доставку до отправки |

Автоматического повторного POST после таймаута нет: в контракте API не заявлен
idempotency key и нет метода поиска результата. Поэтому гарантировать exactly-once
на стороне ShopByShop нельзя. Зависшие `sending` через 10 минут становятся
`uncertain`, а не отправляются заново. Проверка относится к Poland API; существующая
логика создания отправления Европочты не переписывалась.

Команды ниже принимают **внутренний числовой ID заказа из БД**, а не `public_uid`:

```bash
RAILS_ENV=production bundle exec rake 'poland_tracks:status[1001]'
RAILS_ENV=production bundle exec rake 'poland_tracks:retry[1001]'
RAILS_ENV=production bundle exec rake poland_tracks:dispatch
```

`retry` разрешён только для `blocked`: обновляет снимок получателя из исправленного
профиля, сохраняет исторические PLN/URL из позиций и ставит задание в очередь.
Для `uncertain` нужно сначала проверить заказ/трек в ShopByShop:

- Если трек уже создан, сохранить его ответ с обязательными полями в JSON-файл
  и зарегистрировать результат локально без нового POST:

  ```bash
  RESPONSE_FILE=/secure/path/response.json RAILS_ENV=production bundle exec rake 'poland_tracks:resolve_created[1001]'
  ```

- Только после подтверждения, что запрос завершился и трек на стороне ShopByShop
  отсутствует, разрешить повтор исходного снимка:

  ```bash
  CONFIRMED_ABSENT=yes RAILS_ENV=production bundle exec rake 'poland_tracks:resolve_absent[1001]'
  ```

Если сам запрос нужно исправить, сперва устранить неопределённость на стороне API.
Не сбрасывать `sending`/`succeeded` в pending вручную ради повторной отправки.

## Заказы, оформленные до установки

У старых позиций может не быть снимка `poland_price_pln` / `poland_product_url`.
При сборке и отправке экспорта недостающие PLN/URL **дозаполняются из текущего
каталога** (`Product.price` / `Product.url`) и сохраняются на позиции. Уже
заполненный снимок не перезаписывается; цена BYN из `order_items.price` никогда
не подставляется. Если товара в каталоге нет или у него нет цены/URL ≥ 1 PLN,
экспорт остаётся `blocked`.

Минутный `DispatchPolandTrackExportsJob` сам переоткрывает `blocked` с ошибками
вида PLN/URL/weight, когда каталог уже может их закрыть. Ручной запуск:

```bash
RAILS_ENV=production bundle exec rake poland_tracks:heal_blocked
RAILS_ENV=production bundle exec rake 'poland_tracks:retry[ORDER_DATABASE_ID]'
```

Для новых заказов поля сохраняются автоматически. Новые проверки не меняют
текущую форму checkout; если в профиле не собраны личный номер/индекс/дата выдачи
и т. п., данные нужно дополнить через существующий профиль перед повтором экспорта.
Расширение существующей формы регистрации для документов РФ в этот патч не входит.

## Проверки

Добавлены RSpec-сценарии для контракта, BY/RU, оплаты, повтора уведомления,
ожидания трека, обоих курьеров без ПВЗ и типа 5 без трека, выключения интеграции, Redis, отката транзакции,
снимков PLN/получателя, шифрования, дубликатов задач, HTTP-ошибок и неопределённого
результата. Отдельный spec `spec/models/poland_track_export_concurrency_spec.rb` использует два
реальных PostgreSQL-соединения и проверяет один POST. В нём выключены транзакционные
фикстуры, создаются и удаляются только собственные тестовые записи. Нужен пул ≥ 3.
Также есть тест повторного входа worker без потоков.

```bash
RAILS_ENV=test bundle exec rails db:prepare
bundle exec rspec spec/services/poland_tracks \
  spec/models/poland_track_export_concurrency_spec.rb \
  spec/services/webpay_payment_completion_service_spec.rb \
  spec/services/europost_create_shipment_service_spec.rb \
  spec/jobs/europost_create_shipment_job_spec.rb
```

В среде подготовки отсутствуют Ruby/Bundler, поэтому RSpec не выполнен
(`bundle: command not found`). Выполнена статическая проверка синтаксиса Ruby
парсером tree-sitter-ruby; ошибок не найдено. `db/schema.rb` намеренно не
перегенерирован без рабочей БД — обновится при `db:migrate`.
Реальные платежи и POST в production API при подготовке не выполнялись.


## Git-патч и совместная проверка

Патч предназначен для исходного `ikeya_test(7).zip`, до предыдущего архива с
интеграцией. Он включает весь новый функционал, обе миграции, тесты и этот README.
Не накладывать его поверх прежней реализации: `git apply --check` должен пройти
без конфликтов. `.env`, ключи и исходные секреты в патч не входят.

```bash
git apply --check /path/to/ikeya_poland_tracks.patch
git apply /path/to/ikeya_poland_tracks.patch
bash bin/test-poland-tracks
```

Скрипт сначала готовит тестовую БД и проверяет Zeitwerk, затем запускает новые
сценарии и существующие тесты оплаты/отправления Европочты. Работает исключительно
с RAILS_ENV=test, реальный POST в ShopByShop блокируется WebMock.
Если тестовая PostgreSQL БД требует пользователя/пароль, использовать свой
DATABASE_URL, обязательно указывающий отдельную тестовую БД, например ikea_api_test.
Конфигурация test в исходном database.yml не использует DB_HOST/DB_USERNAME.

Прислать полный вывод первой упавшей команды: применимость патча, db:prepare,
Zeitwerk или RSpec с seed и backtrace. Пока RSpec не выполнен, работоспособность
не считается подтверждённой. После зелёного прогона — по одному согласованному
интеграционному заказу каждого типа; это создаёт реальные записи в ShopByShop.
Процент покрытия не заявляется: SimpleCov в исходном проекте не настроен.

SHA-256 исходного ZIP для идентификации базы патча: `9415f1a50db2c07a1c548776ba42a20a6dcdf3263f9a29ca0c997c97534103d3`.
